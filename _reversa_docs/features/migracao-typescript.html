🟦 Migração TypeScript

Tornar o contrato de dados verificável em tempo de compilação, sem alterar comportamento observável.

Feature 001 44/44 ações 0 erros de tipo Cenário legado
Visão geral

A rede de proteção que o projeto não tinha

A unit torna verificável, por um verificador de tipos, o contrato de dados do Prontuário Fácil: as 8 entidades clínicas, os enums fechados de status e tipo, e o contrato único de acesso a dados compartilhado entre o modo online e o offline. Antes, o desenvolvedor único não tinha como saber que havia quebrado um nome de campo, um status ou a fronteira de isolamento por dono antes de o sistema falhar em uso real — o projeto não possui teste automatizado.

Estratégia

Incremental, de dentro para fora

A SPA continua idêntica em runtime, o backend continua sendo o BaaS e nenhum contrato de dados é alterado. A conversão sobe camada por camada, cada etapa reversível e com critério objetivo de aceite (decisão D-06).

Etapa 1Gate de verificação e configuração estrita
Etapa 2Contratos de tipo das entidades (src/types/)
Etapa 3Contrato único de acesso a dados (src/api/)
Etapa 4Componentes
Etapa 5Telas, módulo a módulo
Arquitetura

Duas camadas novas

O código de aplicação deixou de falar com o SDK do BaaS diretamente.

CamadaPapel
src/types/Contratos de dados: as 8 entidades clínicas, a entidade embutida User e os conjuntos fechados (status, tipos, tipo sanguíneo, ações auditadas)
src/api/Contrato único de acesso a dados (AppDataClient) honrado pelas duas implementações: online (SDK) e offline (mock + localStorage)

Regras de negócio

O que passou a ser verificado

RN-01Todo registro persistido tem identificador e data de criação preenchidos pelo servidor; a tela não os define.
RN-02Status de Consulta pertence ao conjunto fechado agendada, em_andamento, concluida, cancelada.
RN-03Status de Agendamento é conjunto fechado e a transição permanece manual (congelamento deliberado D-12).
RN-04Tipo sanguíneo pertence ao conjunto fechado ABO/Rh + desconhecido.
RN-05Tipos de documento clínico e de modelo são fechados: um modelo de atestado não aparece ao emitir receita.
RN-07A leitura de dado clínico exige a declaração do escopo na fronteira de tipos. A autorização real segue na RLS do servidor.
RN-08O usuário do modo offline é uma variante sem papel e sem dono, de forma estrutural e não silenciosa.
Achados

O que a validação revelou

🔴Variável fantasma: {DIAS_AFASTAMENTO} é listada como disponível na UI, mas nunca é interpolada — o editor substitui apenas {PACIENTE_NOME}, {PACIENTE_CPF}, {DATA} e {DATA_EXTENSO}. Fora do escopo, ficou documentado.
🐞Defeito corrigido no fumaça: o adaptador offline não preenchia created_by_id no create — todo registro criado offline ficava invisível para as leituras com escopo.
📐Premissa do plano corrigida: o ponto de partida não era "677 erros em 43 arquivos", e sim 1.324 erros em 81 arquivos — a medição antiga cobria só parte do código-fonte.
